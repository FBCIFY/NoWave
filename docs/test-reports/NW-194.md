# NW-194 — Destinataire du push et changement de compte

Vérification le 20 octobre 2026 sur la base `8fdb36c`.
Purger la file au changement de compte n'empêchait pas un ancien push conservé
par le système d'arriver après la connexion au compte suivant. Le payload ne
portait aucune identité permettant de distinguer son destinataire.

Le worker ajoute maintenant `recipient_firebase_uid`, lu sur l'utilisateur
verrouillé pendant la livraison. Le mobile compare ce destinataire au compte
Firebase courant, avant affichage et avant navigation. Les messages reçus avant
connexion sont revérifiés quand le profil devient prêt. Un ancien objet de
notification gardé en mémoire est soumis au même contrôle.

Les anciennes notifications sans destinataire ne sont plus ouvertes directement :
le message propose l'historique, qui reste filtré par le serveur pour le compte
connecté. Pour la livraison, déployer le worker qui renseigne le nouveau champ
avant de distribuer la nouvelle version mobile. Les anciennes versions mobiles
ignorent ce champ supplémentaire. Aucune migration SQL n'est nécessaire.

Validations :

- `flutter test --no-pub test/core/notifications test/features/alerts` : 147 tests.
- `pytest backend/tests/unit/test_notification.py backend/tests/unit/test_firebase_push_sender.py -q` : 56 tests.
- `pytest backend/tests/database/test_notification_worker.py -q` : 41 tests sur
  une base PostGIS temporaire dédiée, dont contrôle du destinataire issu de SQL.

Les tests couvrent le compte A vers B, une notification initiale pour A alors
que B se connecte, l'ancien format, les doublons, les erreurs et les réessais.
Un avertissement de dépréciation du client de test Starlette est présent.
FCM/APNs réels et notification conservée dans le centre système restent à tester
sur appareil ; aucune livraison ou modification de production n'a été effectuée.
