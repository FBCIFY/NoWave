# NW-214 — Budget séparé pour les tuiles marines

Base : `06b2eea90bb2203b3d50d09fc03866ed5bee7cfb` (`origin/dev`).
Ticket : https://linear.app/blueway/issue/NW-214

## Cause et mesure après cache fonctionnel

Les routes XYZ marines passaient dans le budget général API de 10 req/s/IP,
rafale 30, tandis que les MVT de signalements avaient leur propre budget.
Une recette Nginx natif 1.28.3 en loopback utilise la vraie configuration
(ports, chemins temporaires et adresse d'upstream adaptés localement), un vrai
cache MarineHTTP inscriptible/persistant et un fournisseur synthétique.
Tous les chemins de navigation sont préchauffés avant mesure. Aucun fournisseur
public ni API de production n'est sollicité par ce test.

| Contrôle | Avant | Après |
|---|---:|---:|
| Tuiles de navigation demandées | 147 | 147 |
| HTTP 429 de navigation | 103 | 0 |
| Scénarios profil perturbés par les tuiles | 5/7 | 0/7 |
| Appels fournisseurs pendant cache chaud | 0 | 0 |
| Rafraîchissement après expiration synthétique | 7/7 HTTP 200 | 7/7 HTTP 200 |
| Protection générale sur 55 requêtes de test | 429 maintenus | 429 maintenus |

Ces chiffres portent sur un scénario contrôlé, pas une mesure de charge réelle
sur téléphone. Le cache seul n'élimine pas la contention au proxy. Les logs du
proxy local attestent `limit_req_status=REJECTED` sans 429 amont ; les logs de
production restent indisponibles, donc la provenance précise Nginx/Cloudflare
des 429 distants n'est pas affirmée.

## Correctif minimal

Un budget distinct `marine_tiles_limit` de 20 req/s/IP, rafale bornée à 40,
avec mise en attente au-delà de 8, couvre uniquement les sept familles XYZ et
leurs extensions exactes. Les métadonnées, profils et publications restent à
10/s ; les MVT authentifiés restent à 30/s. Le plafond 30 connexions/IP, les
en-têtes de sécurité et la validation de l'origine sont conservés. Les rafales
marines sont lissées avant l'API. Aucune hausse globale, retry en boucle,
préchargement ou cache téléphone n'est introduit. Le transport fournisseur
et ses TTL/backoff restent inchangés.

## Passe 1 — Technique

- 8 tests réussis, dont exécution du vrai Nginx local avec les scénarios : carte
  stable, déplacements horizontal/vertical, zoom avant/arrière, autre zone,
  retour sur zone, expiration du cache et rafraîchissement.
- HTTP 429 et 503 simulés ; Retry-After numérique, date HTTP et invalide testés :
  aucun appel pendant le cooldown, reprise après échéance, erreurs non cachées.
- Douze requêtes concurrentes identiques : un seul appel fournisseur, 11 hits.
- Aucun signalement ni appel fournisseur public créé pour cette mesure.

## Passe 2 — Régression et intégration (même agent)

- **951 tests API/unitaires réussis, 1 ignoré**, dont le probe Nginx natif activé
  par `NOWAVE_TEST_NGINX`. Aucun échec ; Python 3.12.15.
- Ruff et `git diff --check` réussis. Configuration effective testée par
  `nginx -t` puis par de vraies requêtes HTTP locales.
- Les protections générales rejettent encore une rafale abusive. Les requêtes
  profil pendant navigation réussissent avec le budget séparé.
- Revue des bornes, routes exactes, mémoire de la nouvelle zone (10 Mio),
  plafond de connexions, indépendance des budgets et absence de modification
  des limites fournisseurs.

Le probe est reproductible via `backend/tools/probe_marine_rate_limits.py`.
Le test natif Nginx est ignoré si aucun binaire n'est disponible ; il a été
réellement exécuté localement avec `NOWAVE_TEST_NGINX`. Le seul test ignoré dans
la suite locale est l'archive SHOM XYZ facultative absente.

## Vérification Docker complémentaire — 20 octobre 2026

Les vrais Dockerfiles API/web ont été construits depuis l'intégration locale
avec NW-212/NW-213. Les conteneurs reprennent les restrictions de production
(rootfs read-only, UID 10001/101, capacités supprimées, limites de ressources).
Le réseau Docker est interne. Le proxy charge successivement le fichier Nginx
de la base dev puis celui de cette branche, sans adaptation des règles de débit.
Le service de recette utilise le vrai MarineHTTP et son volume persistant ;
les réponses cartographiques sont des octets synthétiques via MockTransport,
sans fournisseur public. Ce test mesure le réseau/cache, pas le rendu des cartes.

Les sept scénarios donnent à nouveau **103/147 tuiles en 429 avant**, contre
**147/147 HTTP 200 après**, et cinq profils refusés avant contre aucun après.
Dans les deux cas, zéro appel fournisseur pendant la mesure du cache chaud.
Après expiration synthétique : sept tuiles HTTP 200 et sept appels au transport
simulé. Une rafale distincte de 55 requêtes API conserve **24 refus en 429** après
correction. Les logs Nginx confirment 24 rejets locaux sur cette rafale et aucun
429 d'upstream ; aucune tuile de navigation n'est rejetée après correction.

La suite backend intégrée passe aussi contre PostgreSQL 17/PostGIS dans Docker :
**1 235 réussites, 1 archive SHOM facultative ignorée**. Aucun changement de code
supplémentaire n'a été nécessaire. Les preuves locales sont dans
`NoWave-cartography-validation-20261020/docker-rate-{baseline,fixed}.json`,
`docker-nginx-{baseline,fixed}.log` et `docker-backend.xml`. Les conteneurs et
volumes de recette sont retirés sans toucher au conteneur web de l'utilisateur.

## Limites de publication

La branche est indépendante et part de la même base que NW-212/NW-213. Le cache
corrigé a été évalué localement avant ce changement Nginx. Aucun déploiement ni
merge. La recette Android contre le proxy corrigé en production est encore
bloquée par l'absence d'autorisation de déploiement et de logs serveur. Les
compteurs réels et le dimensionnement multi-utilisateur sont à vérifier après
déploiement. Ce correctif ne prouve pas la disparition de tous les 429 publics.
