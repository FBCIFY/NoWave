## 3. Modifications réalisées

- `alert.dart` : modèles Alert/AlertPage/AlertPush et validation des identifiants, version, catégorie, coordonnées GeoJSON et distance. Date obligatoire pour l'historique, facultative pour le push : aucune date inventée. Réutilisation de ReportCategory et du formatage DMS.
- `alert_service.dart` : appel réel authentifié de l'historique avec page/limit ; vérification de la pagination retournée. Aucun fallback fictif.
- `alert_history_controller.dart` : pages sérialisées, déduplication par id ou report/version, conservation des données lors d'une erreur et retry de la page échouée. Un refresh échoué reste réessayable même après la dernière page. Ignore les résultats tardifs après dispose.
- `alerts_screen.dart` : nouvel historique accessible par la cloche de l'accueil, avec états loading/empty/error, catégorie, distance en NM au moment de l'alerte, DMS, date, refresh et page suivante. Garde contre les doubles taps pendant l'ouverture d'une fiche.
- `alert_push_source.dart` : interface injectable et adaptateur Firebase réel pour onMessage, onMessageOpenedApp et getInitialMessage.
- `alert_push_controller.dart` : capture au démarrage avant authentification/profil, puis navigation seulement avec session et accueil autorisés. Files bornées, filtrage des doublons et expiration. Une ouverture attend la fermeture de la précédente. Séparation des déduplications affichage et ouverture : recevoir en foreground ne consomme pas le futur tap.
- `push_notification_listener.dart` : présentation d'une SnackBar catégorie/distance/DMS avec action Ouvrir ; rattachement/détachement du callback de navigation à l'accueil. Le contrôleur possède les abonnements Firebase, pas le widget.
- `main.dart`, `auth_gate.dart`, `profile_gate.dart`, `home_screen.dart` : injection des services réels, démarrage/dispose du contrôleur, gating du profil actif, désactivation pendant déconnexion. Changement de compte/déconnexion invalide la file et les résultats initiaux tardifs et ferme les routes du compte précédent. Un compte suspendu n'ouvre pas les alertes.
- `alert_report_screen.dart` : historique et FCM ouvrent la même fiche ReportDetailSheet. Lecture réelle du report, contrôle d'expiration, puis nouvelle lecture avant ouverture de carte pour ne pas utiliser une position historique ou un report retiré entre-temps.
- `report_detail_sheet.dart` : action optionnelle vers la carte avec protection contre doubles ouvertures, erreur affichée et message 403 explicite ; détail/photo existants conservés.
- `map_screen.dart` : action historique sur la carte principale ; route de carte focalisée sur le report relu, avec retour et accès à sa fiche. Viewport initial centré, sans recentrage GPS automatique. Point GeoJSON sélectionné indépendant des tuiles MVT, retiré à expiration par timer. Cette route focalisée ne partage pas le contrôleur MVT de la carte principale.

## 4. Architecture et flux

Historique : HomeScreen → AlertsScreen → AlertHistoryController → AlertService → ApiService + jeton Firebase → API. Le service concret injectable suit les conventions existantes ; aucun repository parallèle n'a été ajouté.

Push : FirebaseAlertPushSource → AlertPushController (session, expiration, déduplication, file) → PushNotificationListener attaché à HomeScreen → AlertReportScreen → ReportDetailService → ReportDetailSheet → MapScreen existant.

AuthGate possède la durée de vie du contrôleur. ProfileGate l'autorise uniquement après chargement d'un profil actif. Les callbacks de navigation ne sont pas exécutés dans un isolate background. Le détail est toujours relu côté serveur ; la notification ne constitue pas une autorisation d'accès.

## 5. Contrats utilisés

`GET /api/v1/users/me/alerts?page=1&limit=20`, sans body, Bearer ID token Firebase. Réponse : `items` (id, report_id, report_version, category, position Point [longitude, latitude], distance_m, alerted_at), page, limit, total, pages. Les pages suivantes utilisent le même limit. Historique indépendant de la réussite du push ; aucune mutation read/unread. Erreurs HTTP propagées, états UI dédiés notamment 401/403/404, erreur générique pour autres 4xx/5xx, timeout HTTP existant de 10 secondes.

Le détail/photo réutilise les contrats de ReportDetailService, notamment `GET /api/v1/reports/{id}`. Aucun endpoint métier ajouté.

Le prompt ne fixe pas les noms des clés FCM : le contrat de transport suivant est une proposition implémentée côté mobile, à aligner avec le futur worker. Toutes les valeurs data sont des chaînes. Champs requis : alert_id, report_id, report_version, category, position (GeoJSON sérialisé), distance_m, expires_at. Champs facultatifs : position_dms, alerted_at. Le DMS affiché est recalculé depuis les coordonnées validées pour rester cohérent.

Exemple synthétique de payload (les dates sont des fixtures, pas une notification à envoyer) :

```json
{
  "notification": {"title": "Alerte pollution", "body": "Pollution à 1,8 NM"},
  "data": {
    "alert_id": "alert-a",
    "report_id": "report-a",
    "report_version": "1",
    "category": "pollution",
    "position": "{\"type\":\"Point\",\"coordinates\":[5.37,43.29]}",
    "position_dms": "43° 17′ 24″ N · 5° 22′ 12″ E",
    "distance_m": "3334.0",
    "expires_at": "2026-10-10T11:00:00Z"
  }
}
```

L'affichage système en background/terminated dépend d'un message notification + data et de la configuration/permission Firebase/APNs existante. Aucun plugin de notification locale ni support d'affichage système des messages data-only n'a été ajouté. Les taps passent par onMessageOpenedApp/getInitialMessage.

## 7. Gestion des erreurs

Historique vide affiché explicitement ; hors réseau, message clair et retry. Les pages déjà chargées sont conservées avec indication qu'elles peuvent être anciennes, sans prétendre à une disponibilité hors ligne. Timeout/réponse GET perdue restent des échecs réessayables ; aucune opération d'écriture n'est impliquée.

401/403/404/5xx, payload invalide et échec de source FCM ne font pas crasher le parcours. Report expiré même avec réponse 200, retiré/404 ou inaccessible : message dans la fiche. Nouvelle lecture avant carte, avec refus de navigation si le report a disparu. Une erreur de navigation informe et permet de retrouver le report par l'historique.

Déduplication push sur alert_id, couple report_id/version et messageId transport ; affichage et ouverture séparés. Expiration vérifiée à réception, au tap, en sortie de file et au chargement détail/carte. Files limitées à 32 ouvertures en attente ; caches de déduplication limités à 1536 clés et purgés par expiration. Mémoire de session uniquement, pas de garantie persistante entre redémarrages ou après éviction. Déconnexion/changement d'utilisateur efface ces structures ; génération invalide les retours asynchrones de l'ancien utilisateur.

## 10. Écarts / décisions techniques

- Adaptateur HTTP réel dès maintenant ; mocks uniquement en test pour le backend manquant. Aucune implémentation du métier de Vadim.
- Service injectable conforme au dépôt, sans création d'une couche repository artificielle.
- Format FCM explicitement proposé ici, pas présenté comme déjà déployé. alerted_at n'est pas imposé au push ; l'historique le requiert.
- Position carte provenant d'une relecture du report, et non de la position historique de l'alerte. Route MapScreen séparée pour conserver le contexte de navigation précédent ; point GeoJSON indépendant des tuiles.
- Déduplication bornée en mémoire de session ; ni cache hors ligne ni état lu/non lu.
- Pas d'intégration NW-126 sur cette branche créée depuis dev ; NW-128 n'a pas été commencé.
- Aucune dépendance, lockfile, configuration de test ou `.env.json` modifiée.
