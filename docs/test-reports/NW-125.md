## 4. Architecture et flux

Historique : HomeScreen → AlertsScreen → AlertHistoryController → AlertService → ApiService + jeton Firebase → API. Le service concret injectable suit les conventions existantes ; aucun repository parallèle n'a été ajouté.

Push : FirebaseAlertPushSource → AlertPushController (session, expiration, déduplication, file) → PushNotificationListener attaché à HomeScreen → AlertReportScreen → ReportDetailService → ReportDetailSheet → MapScreen existant.

AuthGate possède la durée de vie du contrôleur. ProfileGate l'autorise uniquement après chargement d'un profil actif. Les callbacks de navigation ne sont pas exécutés dans un isolate background. Le détail est toujours relu côté serveur ; la notification ne constitue pas une autorisation d'accès.

## 5. Contrats utilisés

`GET /api/v1/users/me/alerts?page=1&limit=20`, sans body, Bearer ID token Firebase. Réponse : `items` (id, report_id, report_version, category, position Point [longitude, latitude], distance_m, alerted_at), page, limit, total, pages. Les pages suivantes utilisent le même limit. Historique indépendant de la réussite du push ; aucune mutation read/unread. Erreurs HTTP propagées, états UI dédiés notamment 401/403/404, erreur générique pour autres 4xx/5xx, timeout HTTP existant de 10 secondes.

Le détail/photo réutilise les contrats de ReportDetailService, notamment `GET /api/v1/reports/{id}`. Aucun endpoint métier ajouté.

Le prompt ne fixe pas les noms des clés FCM : le contrat de transport suivant est une proposition implémentée côté mobile, à aligner avec le futur worker. Toutes les valeurs data sont des chaînes. Champs FCM obligatoires : alert_id, report_id, report_version, category, position_dms, distance_m, expires_at. Champs facultatifs : position (Point GeoJSON sérialisé) et alerted_at. position_dms est obligatoire conformément à la Technical Documentation. Il est validé puis converti en coordonnées. Si position est fourni, le GeoJSON est validé et comparé au DMS ; sinon les coordonnées proviennent du DMS. Le DMS affiché reste formaté depuis ces coordonnées validées. La stratégie et les formats acceptés sont précisés dans le complément de correction ci-dessous.

Exemple synthétique de payload sans GeoJSON facultatif (les dates sont des fixtures, pas une notification à envoyer) :

```json
{
  "notification": {"title": "Alerte pollution", "body": "Pollution à 1,8 NM"},
  "data": {
    "alert_id": "alert-a",
    "report_id": "report-a",
    "report_version": "1",
    "category": "pollution",
    "position_dms": "43° 17′ 24″ N · 5° 22′ 12″ E",
    "distance_m": "3334.0",
    "expires_at": "2026-10-10T11:00:00Z"
  }
}
```

L'affichage système en background/terminated dépend d'un message notification + data et de la configuration/permission Firebase/APNs existante. Aucun plugin de notification locale ni support d'affichage système des messages data-only n'a été ajouté. Les taps passent par onMessageOpenedApp/getInitialMessage.

## 7. Gestion des erreurs

Historique vide affiché explicitement ; hors réseau, message clair et retry. Les pages déjà chargées sont conservées avec indication qu'elles peuvent être anciennes, sans prétendre à une disponibilité hors ligne. Timeout/réponse GET perdue restent des échecs réessayables ; aucune opération d'écriture n'est impliquée.

401/403/404/5xx, payload invalide et échec de source FCM ne font pas crasher le parcours. Report expiré même avec réponse 200, retiré/404 ou inaccessible : message dans la fiche. Nouvelle lecture avant carte, avec refus de navigation si le report a disparu. Une erreur de navigation informe et permet de retrouver le report par l'historique.

Déduplication push sur alert_id, couple report_id/version et messageId transport ; affichage et ouverture séparés. Expiration vérifiée à réception, au tap, en sortie de file et au chargement détail/carte. Files limitées à 32 ouvertures en attente ; caches de déduplication limités à 1536 clés et purgés par expiration. Mémoire de session uniquement, pas de garantie persistante entre redémarrages ou après éviction. Déconnexion/changement d'utilisateur efface ces structures ; génération invalide les retours asynchrones de l'ancien utilisateur.

## Correction après revue — position DMS obligatoire

État avant correction : branche NW-125 propre, HEAD `6343fed44891a067a4b01dc24e879cae9de24643`. La revue a identifié que position_dms était facultatif, contrairement au contrat documentaire. Correction réalisée sur cette même branche uniquement.

### Contrat et stratégie de cohérence

`AlertPush.positionDms` est désormais requis et non nullable. `fromData` exige une chaîne non vide, vérifie sa syntaxe et compare latitude/longitude DMS au Point GeoJSON lorsqu’il est fourni (voir deuxième correction ci-dessous). Les protections GeoJSON existantes (type Point, deux coordonnées finies, bornes géographiques) sont conservées.

Format accepté : latitude puis longitude, degrés/minutes/secondes et hémisphères N/S puis E/W en majuscules ; séparateur point médian ou virgule ; primes Unicode ou quotes ASCII ; espaces facultatifs entre composants ; secondes entières ou décimales avec point. Exemple canonique : `43° 17′ 24″ N · 5° 22′ 12″ E`. Minutes et secondes strictement inférieures à 60 ; degrés au plus 90/180 ; aux pôles et à 180°, minutes/secondes nulles.

Comparaison numérique sur chaque axe avec tolérance de 0,5 seconde d'arc, plus epsilon de 1e-10 degré pour les flottants. Cela accepte l'arrondi à la seconde entière utilisé par le formateur existant. Une inversion d'hémisphère ou une position différente au-delà de cette tolérance est rejetée. La chaîne reçue est conservée dans le modèle ; l'affichage reste canonique via le formateur des coordonnées validées (GeoJSON si fourni, sinon dérivées du DMS). L'historique n'acquiert pas de nouveau champ requis.

Absence, mauvais type, syntaxe invalide ou incohérence lèvent FormatException au parsing. Le contrôleur existant intercepte cette erreur : aucun affichage d'alerte ni navigation en foreground ; message « notification invalide » lors d'une tentative d'ouverture background/terminated. Aucun crash, aucun identifiant consommé par la déduplication pour le message rejeté. Un message corrigé avec les mêmes identifiants peut ensuite ouvrir la fiche une seule fois.

## Deuxième correction après revue — GeoJSON FCM facultatif

Départ propre sur `feat/NW-125-s3-j2-alerts-fcm`, HEAD `4ed506de69b6acaabcd1ed7eceb7165d8448e93b`. La revue a identifié une contrainte supplémentaire non documentaire : le parsing exigeait position GeoJSON en plus du DMS requis.

Option retenue : conserver AlertPush et son modèle Alert, en dérivant latitude/longitude du DMS validé si position est absent. Le parseur DMS existant retourne maintenant les deux coordonnées signées ; aucune position par défaut n'est inventée. Un DMS absent ou invalide reste rejeté même sans GeoJSON. Lorsque la clé position existe, sa valeur est obligatoirement validée : null, chaîne vide, JSON invalide, mauvais type géométrique, mauvaise dimension, valeurs non numériques ou hors bornes restent des erreurs. Aucun repli vers le DMS ne masque un GeoJSON fourni mais invalide. Si le GeoJSON est valide, sa précision est conservée et la comparaison au DMS maintient la tolérance de 0,5 seconde d'arc (plus epsilon flottant).

Aucun changement de navigation : ouverture par report_id, lecture serveur du détail et nouvelle lecture avant ouverture de la carte. Les coordonnées du push ne remplacent pas celles du signalement relu.
