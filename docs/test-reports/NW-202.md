# NW-202 — Investigation des délais Firebase

Date : 19 octobre 2026 (Europe/Paris). Base d'audit recertifiée : origin/dev
`6b54aa861e5cda93bf9b573c443f5946d230945d`. Parent : feature/NW-174, héritant
NW-172/NW-173. Environnement : Linux/WSL, Python 3.14, firebase-admin 7.6.0,
transports HTTP réels sur boucle locale et doubles pour OAuth/FCM.

## Constat et décision

Le constat CON-033 était « À VÉRIFIER ». Le code du SDK installé et les tests
exécutés démontrent des délais existants ; aucun appel FCM sans timeout n'a été
reproduit. Le worker contourne déjà les retries automatiques Firebase pour
l'envoi. Aucun changement du transport de production ni valeur arbitraire
supplémentaire n'est donc ajouté. Les budgets actuels deviennent explicites et
testés, y compris les délais SDK jusqu'ici absents du README.

| Opération | Budget existant, par phase/tentative | Reprise |
|---|---|---|
| Certificats ID token/cookie SDK | 120 s par défaut ; option SDK httpTimeout | Nouvelle requête HTTP API après 503 |
| Identité SDK : révocation ciblée, suppression, cookie | 120 s par défaut ; option SDK httpTimeout | Retries internes SDK possibles |
| Connexion admin REST mot de passe | 5 s connexion/lecture/écriture/pool | Action utilisateur |
| OAuth worker | 10 s connexion/lecture via Request | prepare au prochain passage worker |
| FCM HTTP v1 | 3 s connexion ; 10 s lecture/écriture/pool | Aucun retry transport, calendrier worker |

Ces valeurs ne sont **pas** des délais globaux muraux. requests/httpx bornent
les phases d'inactivité, pas toute la durée d'un flux. Le SDK Auth peut retenter
une connexion/lecture et certains statuts 500/503 ; OAuth/refresh peut ajouter
d'autres appels. Le plafond global d'une requête Auth n'est pas contractuellement
fixé à 120 s. Le définir plus court demanderait une décision opérationnelle et
une recette VPS ; ne pas l'annoncer comme acquis. Le worker fait OAuth avant
les verrous SQL ; l'appel FCM est effectué pendant la transaction existante.

## Étapes et preuves exécutées

1. Inspection du SDK 7.6.0 : `TokenVerifier` et `Client` lisent httpTimeout,
   défaut 120 ; certificat et client identité vérifiés pour défaut et valeur 5.
2. Serveur HTTP local : première réponse retardée de 150 ms ; SDK configuré à
   30 ms dans le test. TransportError observée en moins de 1 s ; deuxième appel
   accepté. Deux appels serveur, aucune connexion Firebase réelle.
3. Même serveur pour FCM : ReadTimeout devient fcm_network temporaire ; reprise
   réussie. Budget de production 3/10 s et transport retries=0 vérifiés séparément.
4. OAuth : timeout 10 transmis ; erreur neutralisée puis reprise. Connexion
   admin : quatre budgets HTTP de 5 s transmis au client.
5. 7 tests ciblés PASS ; suite complète API/unitaire : 673 PASS. Ruff,
   formatage du nouveau fichier et diff whitespace : PASS.

## Revues et limites

Revue fonctionnelle : budgets existants documentés sans modifier le calendrier
métier de retries, erreurs temporaires et reprises conservées, aucune nouvelle
règle d'authentification. Revue technique : transports réels isolés sur loopback,
ressources fermées, aucun secret/réseau externe ; introspection privée du SDK
limitée aux tests et à la version verrouillée pour détecter une évolution SDK.

Recette VPS/Firebase : NOT RUN (aucun environnement déployé utilisé). Ces tests
ne prouvent ni la latence réseau de production ni la livraison sur téléphone.
PostGIS local BLOCKED, daemon Docker absent. Contrôles CI à consulter sur la PR.
