## 3. Modifications et raisons

- **`ProfileService`** : ajoute `getBoat`, `saveBoat`, `deleteBoat`,
  `deleteAccount`. Avant, il ne gérait que le profil et les préférences.
  Chaque requête récupère le token via l'abstraction existante. Les champs
  facultatifs vides deviennent `null`, le pavillon est normalisé en majuscules.
- **`Boat` / `BoatType`** : modèle minimal du bateau personnel. L'enum existant
  est déplacé vers le domaine profil et réexporté depuis `report_detail.dart`
  afin de préserver les consommateurs existants. Pas de seconde liste des types.
- **`BoatScreen`** : lecture initiale, état vide explicite, formulaire de création
  ou modification, validation du nom/pavillon, attente, erreurs et rechargement.
  La saisie est conservée après erreur d'enregistrement. Un conflit 409 propose
  de relire le bateau, sans PATCH automatique. Le DELETE demande confirmation.
  Après réponse perdue, une lecture explicite permet de vérifier l'état serveur.
- **`ApiService.delete`** : paramètre facultatif `expectedStatusCode`.
  Les nouveaux DELETE exigent exactement 204 ; un 200/202 n'est pas assimilé à
  une suppression terminée. Le comportement des autres appelants reste inchangé.
- **`AccountDeletion`** : orchestre journal local, arrêt des envois, DELETE,
  nettoyage et fermeture Firebase. Une seule exécution simultanée. Avant tout
  DELETE, écrit `[uid Firebase, pending]` dans `account_deletion`. Après 204,
  écrit `confirmed`. Ce journal ne contient aucun token. Un échec d'écriture
  initiale empêche l'envoi. Un échec ultérieur laisse le parcours reprenable.
- **`DeviceRegistration`** : ajoute `pauseForAccountDeletion` (arrêt et attente
  de la file) et `finishAccountDeletion` (FCM + identifiant local). Après le 204
  compte, ne rappelle pas `DELETE devices/current`, car le serveur a déjà
  supprimé les appareils et l'identité Firebase. La déconnexion ordinaire
  conserve son chemin existant.
- **`AccountDeletionScreen`** : confirmation irréversible et annulation avant
  envoi. Après une tentative enregistrée, affiche la reprise, sans retour à un
  profil qui pourrait déjà être supprimé. Erreur et retry explicites ; aucun
  retry automatique ni nettoyage sur une erreur API.
- **`ProfileGate`** : lit le journal avant le profil. Une suppression en attente
  prend priorité sur la création de profil, la suspension et le rafraîchissement
  au retour au premier plan. Après succès, le profil en mémoire est abandonné
  et la fermeture Firebase laisse `AuthGate` revenir à la connexion.
- **`HomeScreen` / `ProfileScreen`** : transmettent le service et le callback.
  Le profil ouvre « Mon bateau » ou le parcours de suppression. Les actions sont
  désactivées pendant une sauvegarde de préférence.

## 4. Architecture et flux

```text
Profil → BoatScreen (état du formulaire)
       → ProfileService (adaptateur HTTP déjà existant)
       → ApiService → /api/v1/users/me/boat

Profil → ProfileGate → AccountDeletionScreen (confirmation)
       → AccountDeletion (orchestration et journal)
       → DevicePositionReporter.stop + DeviceRegistration.pauseForAccountDeletion
       → ProfileService.deleteAccount → ApiService → DELETE /api/v1/users/me
       → 204 → journal confirmed
       → DeviceRegistration.finishAccountDeletion
       → AuthService.signOut → completeSignOut → effacement du journal
       → AuthGate / écran de connexion
```

Les services concrets sont testables via MockClient et les interfaces Dart
existantes (`implements` avec Fake). Ce découpage suit l'architecture réellement
présente : aucun nouveau niveau de repository n'est nécessaire. Le backend
reste responsable de SQL, des appareils, de Firebase et de l'anonymisation.

## 5. Contrats API utilisés

| Route | Entrée | Sortie et traitement |
|---|---|---|
| GET `/api/v1/users/me/boat` | Bearer, sans body | 200 : id/name/boat_type/flag_country ; 404 `boat_not_found` : absence |
| POST même route | JSON boat_type/name/flag_country | 201 Boat ; 409 : conflit, relecture proposée |
| PATCH même route | JSON des trois champs éditables | 200 Boat ; null efface nom/pavillon |
| DELETE même route | Bearer, sans body | 204 obligatoire |
| DELETE `/api/v1/users/me` | Bearer, sans body | 204 obligatoire, seul signal de fin du flux serveur |

Types : `voilier`, `bateau_moteur`, `catamaran`, `semi_rigide`, `jet_ski`, `autre`.
Nom : au plus 100 caractères. Pavillon facultatif : deux lettres ASCII.
Ces validations reprennent le schema existant et ne remplacent pas le backend.
Les champs temporels renvoyés par Boat ne sont pas nécessaires à cet écran.

Les 401/403/404 hors absence bateau, 409, 422 et 5xx remontent comme erreurs.
Les requêtes utilisent le timeout HTTP existant de dix secondes. POST/PATCH
conservent la lecture générique 2xx du client existant et exigent un Boat décodable.

## 7. Erreurs et cohérence

- **Lecture bateau indisponible** : message et rechargement, pas de création
  proposée sur une erreur serveur ou un 404 `user_not_found`/proxy.
- **POST perdu / conflit** : pas de création ou modification automatique
  supplémentaire ; relecture explicite. La contrainte backend d'unicité reste
  responsable d'empêcher un second bateau.
- **PATCH/DELETE bateau échoué** : pas d'effacement optimiste ; saisie conservée
  ou bateau encore affiché, relecture proposée.
- **Compte, toute erreur avant 204** : session et identifiant conservés,
  envois appareils/GPS suspendus, état pending persisté, retry explicite.
- **204 puis échec de stockage ou Firebase local** : état confirmed conservé ;
  la reprise ne renvoie pas le DELETE compte.
- **FCM local échoué après 204** : tentative bornée et journalisée selon le flow
  existant, sans bloquer la fermeture puisque les appareils serveur sont supprimés.
- **Double appui** : boutons désactivés et Future partagé dans l'orchestrateur.
- **Redémarrage simulé** : nouveau contrôleur relit le journal du même UID avant
  tout GET profil. Un journal d'un autre UID n'est jamais appliqué à ce compte.
- Pas de gestion d'expiration d'alertes : hors périmètre de NW-126.

## 9. Problèmes restants et limites

Le contrat ne permet pas de distinguer un token expiré d'une identité supprimée
sur un simple 401. Un 404 profil ne prouve pas non plus la fin de la suppression
Firebase. Le front ne les transforme donc jamais en succès. Une réponse perdue
suivie d'un refus permanent de session laisse l'écran de reprise bloqué avec
message invitant à contacter le support. Une API de statut ou un autre mécanisme
backend de réconciliation nécessiterait un contrat supplémentaire ; il n'a pas
été inventé dans ce ticket front.

La fenêtre entre réception du 204 et persistance de `confirmed` reste soumise
à cette même limite si le processus est tué. SharedPreferences reprend le
stockage existant ; ce n'est pas un journal transactionnel garanti contre une
coupure d'alimentation. Le journal est relu lorsque le même utilisateur atteint
`ProfileGate`. Une session déjà invalidée avant ce gate ne sera pas présentée
comme une suppression confirmée.

Le front utilise les garanties du DELETE 204 spécifiées ; leur réalisation
réelle côté SQL/Firebase/appareils doit être vérifiée en intégration. Aucun
changement de sécurité ou logique backend n'a été fait.

## 10. Écarts et décisions

- Le 404 bateau n'est converti en absence que pour `boat_not_found`, conformément
  au backend inspecté. Cela évite d'interpréter une route absente comme « pas de bateau ».
- Les schemas locaux précisent les champs nom/pavillon omis du prompt ; ils sont
  utilisés sans modifier les contrats serveur.
- Le journal local est ajouté pour que le redémarrage ne mène pas à la création
  d'un profil après suppression SQL partielle.
- Après tentative, pas d'annulation prétendant inverser une suppression
  irréversible. L'annulation explicite reste disponible avant envoi.
- La création et la modification suivent les services concrets déjà présents,
  sans imposer une nouvelle architecture de repositories.
