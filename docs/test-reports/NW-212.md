# NW-212 — Cache marin persistant en production

Référence : `origin/dev` `06b2eea90bb2203b3d50d09fc03866ed5bee7cfb`.
Ticket : https://linear.app/blueway/issue/NW-212

## Cause et changement

Le cache SQLite par défaut est sous le home. Le conteneur API est non-root et
`read_only: true` sans montage de ce répertoire. Une reproduction Linux dans un
espace de noms de montage donne `OSError(30, Read-only file system)` avant tout
appel fournisseur. Avec le même code et un répertoire monté en écriture : succès.
Les logs serveur de production sont indisponibles : cette reproduction démontre
l'incompatibilité de configuration, sans prouver que c'est l'unique cause des
503 actuellement servis en production.

Compose monte uniquement pour l'API le volume `marine-cache`, avec
`MARINE_CACHE_DIR=/var/cache/nowave/marine`. L'image initialise ce dossier pour
`10001:10001`, propriétaire de l'API, afin que Docker copie ses droits dans un
volume neuf. Le montage porte sur le dossier entier, fichiers WAL/SHM compris.
Le reste du système reste en lecture seule. PostgreSQL et ses volumes sont
inchangés ; aucune réduction du TTL, éviction OSM anticipée ou Redis ajouté.

## Passe 1 — Technique

- 31 tests cache/fournisseurs/routes réussis.
- Initialisation, WAL/SHM, lecture après écriture, refus de permission avant
  réseau, erreur SQLite, persistance dans un nouveau processus, expiration TTL
  et minimum OSM de 7 jours (max-age plus long respecté).
- Configuration effective obtenue par `docker compose config --format json` :
  volume API inscriptible au bon chemin, tous les services restent read-only,
  aucun montage du cache sur les autres services.
- Reproduction avec un vrai montage Linux read-only : échec sans volume,
  succès après montage du dossier cache en écriture.
- Ruff et `git diff --check` réussis.

## Limites

La copie initiale des droits et la persistance Docker sont désormais validées
localement. Le Compose de test reprend les restrictions de production, mais
remplace son lancement applicatif et ses fournisseurs par une recette contrôlée ;
ce n'est pas un déploiement complet avec les secrets et services de production.
Ne pas supprimer le volume persistant lors des mises à jour. Un volume déjà
existant avec de mauvais droits nécessite une vérification de son propriétaire.

Aucun déploiement effectué. La validation distante Android/production attend
l'autorisation et le déploiement du backend corrigé. Ce correctif ne résout pas
une éventuelle panne des fournisseurs eux-mêmes et ne touche pas au rate limiting.
