## NW-171 — deux sauvegardes ne partagent plus leur dump

Avant, le répertoire dépendait uniquement de l'heure à la seconde : deux appels
utilisaient le même `database.dump`, y compris deux appels successifs dans la même
seconde. Un échec pouvait également laisser un fichier incomplet sous ce nom.

Après correction, `mktemp -d` réserve un répertoire propre à chaque exécution.
Le dump est écrit dans `database.dump.partial`, contrôlé par `pg_restore --list`,
puis les configurations et journaux sont copiés. Le renommage atomique vers
`database.dump` intervient seulement après réussite de toutes ces étapes.
Les sorties incomplètes sont nettoyées en cas d'erreur ou de SIGTERM/SIGINT.
Les anciennes sauvegardes et le verrou du service quotidien sont conservés.

Les tests démarrent deux vrais processus Bash avec une horloge fixée à la même
seconde et bloquent les deux producteurs avant la fin du dump. Ils vérifient :

- deux répertoires distincts, aucun `database.dump` publié pendant l'écriture ;
- après libération, deux succès et les contenus distincts `dump-one` et `dump-two` ;
- aucun écrasement lors de deux appels successifs dans la même seconde ;
- nettoyage après échec de `pg_dump`, de validation, de copie, de collecte des logs ou interruption ;
- conservation du dump précédent et permissions privées des fichiers/répertoires ;
- sortie sans action lorsqu'aucune version n'est installée.

Les noms de répertoires gagnent un suffixe unique. Le nom final du dump et son
format PostgreSQL restent identiques. Un SIGKILL ou une panne peut laisser un
répertoire incomplet, mais le dump n'est pas publié avant les contrôles.

## NW-183 — le tunnel et les routes publiques font partie de la transaction

Avant, `deploy.sh` déclarait la révision courante et désactivait son rollback,
puis `ci-deploy.sh` activait le tunnel et vérifiait les routes publiques. Un échec
de ces dernières étapes ne rétablissait donc pas l'ancienne version.

Après correction :

1. Le jeton tunnel et l'état du tunnel existant sont contrôlés avant activation.
2. Les configurations précédentes de l'application et du tunnel, ainsi que la
   révision déclarée, sont mémorisées pour cette tentative.
3. La transaction couvre les migrations, les services, le worker FCM,
   les contrôles privés, l'activation du tunnel et les trois contrôles publics.
4. Les routes publiques doivent annoncer la version attendue du site et de
   l'API, et une base prête. Les erreurs temporaires conservent les reprises.
5. La révision courante n'est remplacée atomiquement qu'après réussite des
   contrôles et de l'installation du service de sauvegarde.
6. En cas d'erreur ou d'interruption, la version précédente et sa configuration
   tunnel sont restaurées. Le tunnel précédent est relancé seulement s'il
   fonctionnait auparavant. La version restaurée est vérifiée sur l'origine
   privée et, si son tunnel était actif, sur les routes publiques.

Les tests injectent un échec de migration, d'origine privée, de révision du
worker, de démarrage du tunnel, de HTTP public, de version publique, de readiness
publique et de systemd. Ils vérifient les configurations restaurées, les révisions
des services et la révision déclarée, sans message de succès trompeur.
Ils couvrent aussi :

- succès d'une mise à jour et d'une première installation ;
- reprise après une indisponibilité publique temporaire ;
- tunnel précédent absent ou volontairement arrêté ;
- première installation échouée, même avec d'anciens fichiers de secours résiduels ;
- absence du jeton, impossibilité de déterminer l'état du tunnel et verrou de déploiement occupé ;
- erreur du rollback ou indisponibilité publique persistante, explicitement signalées ;
- SIGTERM pendant les contrôles publics ou juste après publication du marqueur ;
- exécution par l'entrée CI, pour vérifier que le défaut d'origine ne réapparaît pas.

Sans version précédente, les nouveaux services applicatifs et le tunnel sont
arrêtés ; la base et ses volumes sont préservés. Aucune restauration automatique
des données ni migration descendante n'est ajoutée. Les migrations doivent
rester compatibles avec la version applicative de secours.

## Reproduction et limites des preuves

Les tests exécutent les vrais scripts dans un système de fichiers temporaire.
Seuls les chemins de production et le contrôle de privilèges sont adaptés à la
sandbox ; le bootstrap système est neutralisé. Bash, `mktemp`, copies,
renommages et verrous système fonctionnent réellement. Docker, les réponses
HTTP, systemd et l'horloge sont simulés aux frontières. Sur ce Mac, une petite
adaptation utilise `fcntl.flock` ; sur Linux, le vrai utilitaire `flock` est utilisé.
Ces résultats ne constituent pas un exercice de rollback sur le VPS réel.

```bash
.venv/bin/python -m pytest backend/tests/api backend/tests/unit -q
```

Pour comparer avec l'ancienne version, extraire ses scripts puis réutiliser
exactement les mêmes tests :

```bash
baseline=$(mktemp -d)
git archive 6b54aa861e5cda93bf9b573c443f5946d230945d deploy/hostinger | tar -x -C "$baseline"
NOWAVE_SCRIPT_TEST_SOURCE="$baseline/deploy/hostinger" \
  .venv/bin/python -m pytest backend/tests/unit/test_deployment_transaction.py -q
```

La seconde commande doit échouer : c'est la démonstration des régressions sur
les scripts d'origine. Le premier lancement de la suite complète a été bloqué
par Jinja2 absent du venv ; l'installation de la version déjà déclarée
`jinja2==3.1.6` a permis l'exécution complète. Le diagnostic initial est conservé
dans [collection-missing-jinja.log](evidence/NW-171-NW-183/collection-missing-jinja.log).
