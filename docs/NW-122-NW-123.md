## Vérifications exécutées

La base utilisée est le conteneur éphémère `nowave-nw122-tests-database-1`,
avec `compose.test.yaml`, sur le port 55433. Chaque suite crée puis supprime sa
propre base `nowave_test_<uuid>`. Aucune donnée de recette ou de production n'est
utilisée. Le transport FCM des tests est simulé ; aucun push réel n'est envoyé.

Les vérifications couvrent notamment : seuil inclusif de 18 520 m, précision,
multi-appareils, consentement et suspension, rollback/idempotence, tâches non
committées, token renouvelé, verrous entre workers et face aux modifications
d'éligibilité, droits du rôle runtime, retries et expiration, erreurs permanentes,
purge sans perte d'historique, arrêt brutal du processus puis reprise avec les
mêmes identifiants. Les deux modes de publication ont été exercés jusqu'à
l'acceptation FCM simulée, avec un premier échec HTTP 503 et `Retry-After`.
Le démarrage sans identifiants Firebase et l'arrêt SIGTERM ont été testés dans
un processus distinct. Le worker conserve la tâche et s'arrête normalement.

Une alerte Starlette préexistante concerne la future utilisation de `httpx2`
dans son client de test ; elle n'a pas fait échouer les suites.
L'environnement Python principal ne contenait pas Jinja2, maintenant requis par
`dev` : Jinja2 3.1.6 a été installé dans un répertoire temporaire pour ces essais.
Le premier scénario d'expiration PostGIS modifiait une date immuable : il a été
corrigé pour créer un signalement déjà expiré, puis les tests ont été relancés.

## Reproduire

Avec les dépendances de `backend/requirements-test.txt` installées :

```sh
python -m pytest backend/tests/api backend/tests/unit -q
ruff check backend
docker compose -f compose.test.yaml -p nowave-nw122-tests up -d --build --wait database
NOWAVE_TEST_ADMIN_URL=postgresql://nowave_ci:ci-test-only@127.0.0.1:55433/nowave_ci python -m pytest backend/tests/database -q
docker compose -f compose.test.yaml -p nowave-nw122-tests down --volumes
```

Depuis `mobile/` :

```sh
flutter pub get --enforce-lockfile
flutter analyze --no-pub
dart format --output=none --set-exit-if-changed lib test
flutter test --no-pub
```

Les rapports de cette exécution sont conservés localement dans
`test-results/alerts/` (répertoire ignoré par Git).

## Limites et étapes restantes

La validation locale ne prouve pas les droits FCM/APNs réels, l'affichage sur
téléphone ou la réception en arrière-plan. Ces essais nécessitent les appareils
de recette et un envoi explicitement ciblé. Vérifier alors publication manuelle
et photo, application ouverte/fermée, ouverture du signalement et expiration.

Les verrous restent détenus pendant l'appel FCM : une action concurrente peut
attendre la fin de cet appel. Cette approche privilégie la cohérence du MVP ;
elle doit être mesurée sous la charge réelle avant toute augmentation de débit.
Les limites réseau sont des délais par opération, pas une garantie de durée
totale face à un serveur qui répondrait très lentement par fragments.

La livraison reste locale : branche NW-122 puis branche NW-123 dépendante.
Aucun push, aucune PR ni mise à jour Linear, aucun déploiement et aucune fusion
dans `dev`. La revue par un autre membre et la validation après intégration
restent à effectuer ; les tickets ne sont pas déclarés terminés dans Linear.
